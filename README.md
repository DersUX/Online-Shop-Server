# Online Shop Server

Бекенд для тестирования и работы Unity-проекта **Online Shop**, созданный с помощью **GPT-6.1 SOL**.

Сервер на ASP.NET Core Minimal API, собранный специально для этого Unity-проекта. Обеспечивает авторизацию, загрузку каталога и баланса игрока, а также покупку товаров за внутриигровую валюту через REST API.

Логика разделена на HTTP-маршруты, сервисы, доменные модели и хранилища. Данные хранятся в памяти и сбрасываются при перезапуске сервера. Формат JSON совместим с Unity JsonUtility.

## Возможности

- Авторизация по логину и паролю с выдачей токена сессии.
- Получение данных игрока и актуального баланса.
- Каталог из 1000 товаров семи типов с названием, описанием и ценой.
- Покупки с проверкой баланса и обновлением инвентаря на сервере.
- Повтор запроса покупки без повторного списания средств.
- Независимые сессии аккаунта и выход из текущей сессии.
- Автоматическая очистка истёкших сессий и ограничение частоты запросов входа.
- Единый формат ошибок для обработки в Unity-клиенте.

## Архитектура

- `Endpoints` — HTTP-маршруты, проверка формата запросов и преобразование результатов в DTO.
- `Services/PurchaseService` — получение аккаунта, поиск товара в каталоге и передача результата в доменную операцию покупки.
- `Services/AuthenticationService` — проверка учётных данных; `AccountStore` отвечает за хранение аккаунтов.
- `Services/SessionCleanupService` — периодическое удаление истёкших сессий.
- `Models/PlayerAccount` — баланс, инвентарь и история; покупка и снимок состояния защищены общей блокировкой.
- `Storage` — аккаунты, неизменяемый каталог и сессии в памяти.
- `DemoData` — создание тестовых аккаунтов и каталога; хранилища получают начальные данные через конструкторы.
- `Security/AccountCredentials` — создание соли и хеша пароля для аккаунта.
- `Security` — проверка паролей и аутентификация сессий.

Модели не зависят от HTTP и DTO. Баланс и коллекции аккаунта недоступны для внешнего изменения;
успешная покупка сохраняет неизменяемый результат для повторных запросов.
`Good` и `PlayerAccount` проверяют свои инварианты при создании. Свойства товара доступны
только для чтения. `PurchaseResult` создаётся через фабрики: успех всегда содержит чек,
ошибка — только статус. DTO сгруппированы по функциональности и имеют суффикс `Dto`.

## Запуск

1. Клонируйте репозиторий сервера.
2. Установите **.NET SDK 8.0**. Для запуска требуется среда выполнения ASP.NET Core 8.0, которая входит в этот SDK.
3. В каталоге с `OnlineShopServer.csproj` выполните:

```powershell
dotnet run
```

По умолчанию сервер доступен по адресу `http://localhost:5000`.
Адрес можно изменить через конфигурацию `urls`, например:

```powershell
dotnet run -- --urls http://localhost:5050
```

## Быстрая проверка API

Сначала выполните вход, затем передайте токен в защищённые запросы:

```powershell
$baseUrl = 'http://localhost:5000'
$session = Invoke-RestMethod -Method Post -Uri "$baseUrl/auth/login" `
    -ContentType 'application/json' -Body '{"login":"player","password":"player123"}'
$headers = @{ Authorization = "Bearer $($session.sessionToken)" }
Invoke-RestMethod -Uri "$baseUrl/player" -Headers $headers
Invoke-RestMethod -Uri "$baseUrl/items" -Headers $headers
Invoke-RestMethod -Method Post -Uri "$baseUrl/purchases" -Headers $headers `
    -ContentType 'application/json' -Body '{"goodId":1,"requestId":"demo-purchase-1"}'
Invoke-RestMethod -Method Post -Uri "$baseUrl/auth/logout" -Headers $headers
```

Пример покупки уменьшает баланс `player` с 1000 до 900 при первом выполнении
после запуска сервера. Повтор с тем же `requestId` не списывает деньги снова.

## Тестовые аккаунты

| Логин | Пароль | Начальный баланс |
|---|---|---|
| player | player123 | 1000 |
| poor | poor123 | 50 |

Аккаунты, баланс, инвентарь, история покупок и сессии хранятся в памяти.
Перезапуск сервера сбрасывает их. Повторный вход баланс не сбрасывает.
Пароли в памяти представлены PBKDF2-хешами с индивидуальной солью;
приведённые в исходниках пароли — публичные тестовые данные.
HTTP используется для локального тестирования; для удалённого сервера используйте HTTPS.

## API

Запросы с телом используют `Content-Type: application/json`.
Все endpoints, кроме входа, требуют `Authorization: Bearer <sessionToken>`.
JSON использует camelCase, коллекции — массивы внутри объектов для Unity JsonUtility.
Реализованы только перечисленные ниже маршруты: регистрации, пополнения баланса,
получения инвентаря и истории покупок через API нет.

### POST /auth/login

```json
{"login":"player","password":"player123"}
```

Ответ `200 OK`:

```json
{
  "sessionToken":"случайный-токен",
  "serverTime":"2026-10-05T11:00:00+00:00",
  "expiresAt":"2026-10-05T12:00:00+00:00"
}
```

Сессия действует один час с момента входа без автоматического продления.
Истёкшие сессии удаляются фоновым сервисом раз в минуту; токен перестаёт действовать
сразу по истечении срока, независимо от очистки.
На сервере установлен общий лимит: 30 запросов входа за минутное окно,
включая некорректные запросы. Превышение даёт `429 too_many_requests` без очереди;
повторите вход в следующем окне. Другие маршруты этот лимит не затрагивает.
Лимит общий для всех клиентов одного процесса; для многопользовательского развёртывания
потребуются отдельные политики ограничения клиентов.
`serverTime` — серверное время создания сессии в UTC; `expiresAt` вычисляется от него.
Клиент получает оставшееся время как `expiresAt - serverTime` и отсчитывает его
монотонным таймером (например, Time.realtimeSinceStartupAsDouble), учитывая сетевую задержку.
Каждый вход создаёт независимую сессию. Токен — случайная строка из 64
шестнадцатеричных символов; передавайте её целиком с сохранением регистра.
Логин чувствителен к регистру и не обрезается: от 1 до 64 символов,
не может состоять только из пробелов. Пароль — от 1 до 256 символов.
Нарушение этих ограничений даёт `400 invalid_request`, неверные данные —
`401 invalid_credentials`.
Ответ входа содержит только данные сессии. Игрока и баланс запрашивайте через `/player`,
каталог товаров — через `/items`.

### GET /items

`GET /items` возвращает `200 OK` и объект `{"goods":[...]}` с 1000 товарами.
Без действующего токена запрос возвращает `401 unauthorized`.

Один товар:

```json
{"id":1,"header":"Меч","description":"Острый меч","price":100,"typeId":7}
```

`typeId` — числовое значение enum `GoodType`: 0 — Unknown (резерв),
1 — Bow (Лук), 2 — Potion (Зелье), 3 — Helmet (Шлем), 4 — Armor (Броня),
5 — Boots (Ботинки), 6 — Shield (Щит), 7 — Sword (Меч).
Эти значения фиксированы и должны совпадать с enum клиента.
Каталог повторяет семь шаблонов: меч, щит, зелье, шлем, лук, броня, ботинки.
Порядок товаров случайно перемешивается при запуске сервера и сохраняется до перезапуска.
ID и характеристики предметов при перемешивании не меняются.
ID товаров — от 1 до 1000. Для товара с ID `id` номер группы равен
`(id - 1) / 7` с целочисленным делением;
цена — базовой цене шаблона + номер группы × 25. Название и описание не меняются.

| Шаблон | typeId | Базовая цена |
|---|---|---|
| Меч | 7 | 100 |
| Щит | 6 | 150 |
| Зелье здоровья | 2 | 50 |
| Шлем | 3 | 80 |
| Лук | 1 | 120 |
| Броня | 4 | 200 |
| Ботинки | 5 | 70 |

### GET /player

Ответ `200 OK` — актуальное состояние аккаунта:

```json
{"id":1,"login":"player","balance":900}
```

### POST /purchases

Покупка одной единицы товара, повторные покупки разрешены:

```json
{"goodId":1,"requestId":"unique-operation-id"}
```

Ответ `200 OK`:

```json
{"requestId":"unique-operation-id","goodId":1,"price":100,"balance":900,"quantity":1}
```

Сервер определяет аккаунт по сессии, цену по каталогу, атомарно проверяет баланс,
списывает деньги и выдаёт товар. Клиент не задаёт цену или баланс.
`goodId` — положительное целое число; ID вне каталога даёт `404 good_not_found`.
`requestId` — строка от 1 до 128 символов, не состоящая только из пробелов,
уникальная для новой операции в рамках аккаунта. Регистр учитывается, пробелы не обрезаются.
`quantity` — общее количество единиц именно этого товара в инвентаре после покупки.
Повтор успешной покупки с тем же ID и товаром возвращает исходный ответ без списания.
Баланс и количество в исходном ответе могут устареть после других покупок; актуальный баланс — в `/player`.
Повтор с другим товаром даёт `409 request_id_conflict`.
Неуспешные покупки не сохраняются; их можно повторить.
История общая для всех сессий аккаунта до перезапуска сервера.

### POST /auth/logout

Без тела. Ответ `204 No Content`. Завершает только текущую сессию.

## Ошибки

```json
{"code":"insufficient_funds","message":"Недостаточно средств"}
```

| HTTP | code | Причина |
|---|---|---|
| 400 | invalid_request | Некорректный JSON или поля запроса |
| 401 | invalid_credentials | Неверный логин/пароль |
| 401 | unauthorized | Нет токена, он неверный, истёк или завершён |
| 404 | good_not_found | Товар не найден |
| 404 | not_found | Маршрут не найден |
| 405 | method_not_allowed | HTTP-метод не поддерживается маршрутом |
| 415 | unsupported_media_type | Неподдерживаемый Content-Type тела запроса |
| 409 | insufficient_funds | Не хватает денег |
| 409 | request_id_conflict | ID покупки уже связан с другим товаром |
| 429 | too_many_requests | Превышен общий лимит запросов входа |
| 500 | internal_error | Непредвиденная ошибка сервера |

Непредвиденные исключения записываются в серверный журнал. Ответ клиенту не содержит деталей исключения.

## Подключение Unity-клиента

В настройках Unity-проекта укажите адрес запущенного сервера. Основные пути API: `/auth/login`, `/player`, `/items` и `/purchases`.

1. Выполнить вход и сохранить sessionToken в памяти клиента.
2. Передавать его в Authorization через UnityWebRequest.SetRequestHeader.
3. Загрузить каталог через `/items`, данные игрока и баланс — через `/player`.
4. Для новой покупки генерировать requestId (например, Guid).
5. При сетевом повторе сохранить тот же requestId. Для повтора старой покупки или параллельных покупок запросить актуальный баланс через `/player`.
6. При `401 unauthorized` очистить токен и показать вход.

## Автоматическая проверка

```powershell
dotnet build
dotnet run --project Verification/Verification.csproj
```

HTTP-сценарии основного API запускают и завершают отдельный сервер на свободном локальном порту,
поэтому сценарии не разделяют баланс, покупки или сессии. Запускается собранная DLL
без вложенного `dotnet run`. Ожидание готовности ограничено 20 секундами и проверяет
ответ `401 unauthorized` от `/items`; при таймауте или раннем завершении выводится журнал сервера.
Порт назначается самим Kestrel при запуске на `127.0.0.1:0` и считывается из журнала запуска.
Отдельные сценарии проверяют одновременный запуск на разных портах и диагностику ошибки запуска.
Каждый сценарий выводит `PASS` или `FAIL`; ошибка не отменяет остальные проверки.
При любой ошибке процесс проверки завершается с ненулевым кодом.
Если запущенный сервер блокирует сборку, используйте отдельную конфигурацию:
`dotnet run --project Verification/Verification.csproj --configuration Verification`.
Проверяет вход, авторизацию, контракт каталога и игрока, покупки, ошибки запросов,
повторы без повторного списания, параллельные покупки, изоляцию аккаунтов и выход
из одной сессии без завершения другой. Также проверяет границы полей, количество товаров,
неизменность старого ответа покупки и повторное использование requestId после ошибки.
Дополнительно проверяются инварианты моделей, цены всех товаров, независимость requestId
между аккаунтами и количество каждого товара в инвентаре.
Истечение сессии проверяется отдельно
через `SessionStore` и тестовые часы, без ожидания часа и HTTP-запросов.
Также проверяются очистка истёкших сессий, HTTP-ошибки `400/401/404/405/415/429`
и доступность защищённых маршрутов при исчерпанном лимите входа.

Правила форматирования и именования заданы в `.editorconfig`.

`Verification` — консольный набор проверок без тестового фреймворка: `dotnet test`
не выполняет эти сценарии. Используйте приведённую выше команду `dotnet run`.
GitHub Actions (`.github/workflows/verify.yml`) при push и pull request собирает оба проекта,
проверяет форматирование и явно запускает `Verification`. Ошибка любого шага завершает CI неуспешно.

Дополнительно проверяются хранилища с пользовательскими начальными данными, запрет повторяющихся
ID и логинов, количества и балансы в чеках параллельных покупок. Ответ `500 internal_error`
проверяется на отдельном сервере внутри процесса проверки с намеренно падающим маршрутом;
в основном API такого маршрута нет.
